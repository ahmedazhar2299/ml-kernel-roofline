# Metrics and assumptions

Each benchmark row records the operation, input size, device, precision, implementation variant, median execution time, throughput, modeled bytes moved, estimated bandwidth, arithmetic intensity, maximum absolute error, and worker-thread count. GPU rows use zero in `worker_threads` because the kernels manage GPU execution through Metal.

- **GEMM operations:** `2 × N³` floating-point operations for an `N × N` matrix product.
- **Elementwise operations:** one operation per element for addition or multiplication. The naive custom variants use scalar-per-element loops; optimized variants use unrolled CPU loops or four elements per Metal thread. These are reported as GFLOP/s for consistency, with the operation count stated explicitly.
- **GEMM traffic model:** The naive kernel counts two input reads per multiply and one output write. The optimized CPU kernel uses 32×32 tiles; the optimized Metal kernel uses 16×16 tiles. Their per-kernel estimates use the respective tile counts and element size (four bytes for FP32). The PyTorch baseline uses an idealized one-read-per-input estimate of `3N²` elements in FP32.
- **2D convolution:** NCHW input with 8 input channels, 16 output channels, a 3×3 filter, stride one, and one-pixel zero padding. Size is the square input width. FLOPs count each multiply and add separately. Modeled bytes count input, weights, and output once.
- **Softmax:** 256 rows, with size as row width. Arithmetic intensity uses an approximate five arithmetic operations per element; exponentials are not weighted as more expensive than additions or multiplications.
- **LayerNorm:** 1,024 rows, with size as the feature count. Normalization uses population variance and epsilon `1e-5`, without learned scale or bias. FLOP and traffic values are approximate.
- **Fused multiply-add traffic model:** Naive custom CPU and Metal variants perform multiply and add as separate passes, counting six vector transfers per element. Optimized custom variants fuse the operations and count three input reads and one output write, or four transfers per element. The eager PyTorch baseline also materializes an intermediate and counts six transfers per element.
- **Elementwise traffic model:** Addition and multiplication count two input reads and one output write.
- **Estimated bandwidth:** modeled bytes divided by median execution time.
- **Arithmetic intensity:** operation count divided by modeled bytes. A fused multiply-add counts as two floating-point operations per element.
- **Numerical error:** The PyTorch results are compared with an FP32 CPU reference. Custom GEMM and fused multiply-add variants are compared with an FP32 CPU reference using the same generated inputs.
- **CPU thread count:** Native CPU kernels use up to the available hardware threads, limited by output row blocks for GEMM or vector elements for elementwise operations. PyTorch reports its configured CPU thread count.

These estimates help compare implementations and place points on a Roofline plot, but they are modeled traffic, not hardware-counter measurements. Cache behavior, compiler transformations, and launch overhead are not measured. The PyTorch GEMM estimate is intentionally idealized, so it should not be interpreted as measured device traffic.

For GEMM, the notebook plots arithmetic intensity using compulsory tensor traffic: one read each of A and B, plus one write of C. This makes the plotted intensity comparable to the 200 GB/s main-memory bandwidth reference. The CSV's per-kernel modeled traffic remains available for estimated bandwidth and other analyses, but it may count cache-served loads as if they came from main memory. The notebook uses the best selected measured GEMM throughput for each device as an empirical compute ceiling unless a sourced compute peak is entered. The intersection of that ceiling with the 200 GB/s memory-bandwidth reference defines the ridge point. Since the compute ceiling is empirical and the bandwidth is a published peak, the plot is an illustrative Roofline model rather than a calibrated hardware Roofline.
